## 四、核心问题诊断：为什么同一个视频分数差 23 分？

这是你最担心的点，用数据说话。

### 4.1 18 次评分真实分布（SQLite 实查）

```
总分：46.0 → 56.6 → 43.0 → 40.2 → 43.7 → 43.2 → 41.2 → 40.6 → 39.0 → 38.6
     → 45.4 → 44.2 → 37.2 → 41.0 → 33.6 → 39.6 → 33.9 → 38.8
均值 ≈ 41.2，极差 = 56.6 - 33.6 = 23.0 分
```

四维分项里摆动最大的是 **D2 讲授语言**（1.6–3.4，摆动 1.8 分 / 0–5 制 = 36%），其次 D1 教学设计（1.0–2.25）。D3/D4 相对稳（因为 OCR/pose 是确定性规则提取）。

### 4.2 根因（按贡献度排序）

1. **LLM 采样随机性（主因，~60%）**：temperature=0.2 不是 0，四维并行各调一次 DeepSeek，每次采样路径不同；D2 又最依赖"对 ASR 文本流畅度的主观判断"，所以摆动最大。DeepSeek API 当前不支持固定 seed。
2. **RAG 召回片段漂移（~20%）**：top_k=4，BGE embedding 本身是确定性的，但 query 字符串里 lesson/lesson_type 若前后端传值不同，召回片段就不同，导致注入 prompt 的"课标依据"在变。
3. **Reflexion 几乎不起作用（~10%）**：它只问"你有没有幻觉"，没有"你和上一次同视频评分差多少"的自洽检查。
4. **多模态感知本身是确定性的（~10%）**：ASR/OCR/pose 跑同一段 mp4 结果字节级一致（datasets 下 12 份 senses JSON 几乎等长），所以感知不是波动源——**波动 100% 来自 LLM 打分环节**。

### 4.3 这意味着什么

**这不是 bug，是"用 LLM 当评分器"的固有特性**。文献 I4（Nkoyo 2025 综述）明确指出 rubric drift 是 LLM 自动评分的已知风险。你现在的系统在"方向上大体稳定"（33–56 都在"待改进"区间），但绝对分数不可复现。**比赛时这是致命伤——评委上传同一个视频两次看到不同分数，直接质疑技术实现分（30%）。**

## 六、10 个青教赛讲课视频（~20 分钟/个）使用计划

### 6.1 不要一次性全跑，分三批用

**第一批（2 个，校准用）—— Week 2 D14 前**
- 选 1 个"上届优秀"（高分示范）+ 1 个"普通"（中等水平）。
- 人工先打金标准分，跑系统，调 prompt/采样。
- 目的：验证 20 分钟视频链路 + 校准评分尺度。

**第二批（4 个，多样性测试）—— Week 3**
- 覆盖不同学科（数学/语文/英语/物理至少各 1）、不同课型（新授/复习/习题）、不同水平（优/中/弱）。
- 每个跑 2 次系统评分，测同视频二次一致性。
- 重点看：ASR 在不同口音/方言下的 WER、OCR 在不同板书风格（粉笔/白板/PPT）下的召回、pose 在不同教姿（走动多/站桩）下的稳定性。

**第三批（4 个，压力测试 + 案例库）—— Week 4**
- 选有"典型问题"的视频：口头禅多的、板书乱的、互动少的、全程念 PPT 的。
- 验证 evidence_check 的硬规则能不能准确抓到这些问题。
- 经专家复评后，通过 `recycle_disputed_case` 回流入 Chroma，**变成"争议课例"知识库**——这本身就是创新点。

### 6.2 入库前必须做的预处理

1. **脱敏**：视频里如果有真实学生正脸、姓名牌，裁掉或模糊（项目文档 §六风险表要求）。
2. **元数据登记**：每条视频在 `datasets/` 下建 `meta.json`（学科/学段/课题/课型/时长/人工金标准分），不要只靠文件名。
3. **不要和 demo 视频混在 uploads/**：单独建 `datasets/qingjiao_sai/`，方便批量跑。
4. **感知结果全部落盘**（现在已有 senses_store），后续调 prompt 时可以**复用同一份 ASR/OCR/pose 结果**，只重跑 LLM 打分——这能省掉 80% 的感知时间，是做 prompt 迭代的关键。

### 6.3 一个重要的架构建议

现在每次上传都会重跑 ASR/OCR/pose。建议加一个**感知结果缓存层**：以视频文件 hash 为 key，把 senses JSON 存起来；同一文件第二次直接读缓存，只跑 LLM。这样：
- 调 prompt 时秒级迭代；
- 10 个视频跑完一遍后，后续每轮回归只花 LLM 的钱（~6 次 DeepSeek 调用/视频，成本 < 1 元）。

| ASR 只输出文本+语速+口头禅 | 抓不到"提问质量"（是不是真问了，还是自问自答） | 在 ASR segments 里加"问句识别"（结尾语气词+标点），区分真互动 vs 假互动 |
| OCR 只做文字去重 | 不知道板书"什么时候写的"、"和讲授是否对应" | 保留每帧时间戳，输出"板书演化时间线"，供 D3.4 内容呼应指标用 |
| 姿态只输出聚合指标 | 20 帧均值会抹平"前 5 分钟紧张、后 15 分钟放松"的变化 | 输出按教学环节分段的姿态曲线（配合 timeline），报告里画折线图 |
| 时间轴只切环节 | 不知道每个环节时长合不合理（导入超过 5 分钟就是问题） | 加环节时长合理性规则（导入≤3min/新授占比 60–70%/小结≥1min） |

### 7.2 评价层补强项

| 现状 | 改进 |
|---|---|
| 四维各打各的，没有交叉校验 | 加一个"一致性检查"：ASR 里没有提问词但 D1 给了高分 → 降 D1 分；OCR 板书空但 D3 给了 3 分 → 强制 D3 ≤ 1.5 |
| Reflexion 只查幻觉 | 改为"对照证据查"：每个维度评分必须能引用 ASR/OCR/pose 里的具体证据片段，引用不到就降分 |
| 没有"难度感知" | 输入学科+学段+课题后，RAG 召回该课的课标要求，评分锚点随课题变化（小学数学和高中物理不能一个尺度） |

### 7.3 工程层补强项

- **任务队列**：现在同步跑，20 分钟视频必超时。用 FastAPI BackgroundTasks + SQLite 任务表就够，不用上 Celery。
- **超时与重试**：LLM 调用加 30s 超时 + 1 次重试；ASR/OCR/pose 任一失败不阻断主流程（现在已有 try/except，但要在前端显示"板书识别失败，D3 置信度低"）。
- **日志聚合**：trace JSONL 已有，但前端看不到。教师端加一个"系统日志"页，能按 trial 回放完整 pipeline。

## 八、对照大赛评分准则的创新点与完成度建议

评分准则：**创新性 30% / 技术实现 30% / 实用性 25% / 用户体验 15%**。

### 8.1 技术实现（30%）—— 当前最扎实，但要把"做了什么"讲清楚

评分点包含：提示词编写、知识库构建、工作流编排、插件/工具集成及应用、智能体功能完整性。

你现在的代码里**每一条都有对应实现**：
- 提示词编写：`llm_client.py` 系统提示 + `evaluator.py` 四维分维度 prompt + `chat/service.py` 双角色 prompt。
- 知识库构建：49 文档 / 12,423 片段 / Chroma / BGE / 增量入库 / OCR 回退。
- 工作流编排：LangGraph 11 节点图。
- 插件/工具集成：自研 ToolRegistry + ASR/OCR/pose/timeline 四工具热插拔。
- 智能体功能完整性：规划/检索/记忆/反思/证据链/分流/复评/回流。

**答辩时要画的图**：就用 `docs/智能体主干架构说明.md` 里的图，但要在图上把"证据链 + A/B/C 分流 + KB 回流"这三个**很多同类项目没有**的模块高亮出来。

### 8.2 创新性（30%）—— 你现在有 3 个真创新点，要讲透

1. **人机协同的"分流 + 回流"闭环**（最硬的创新点）：
   - 机器先评 → evidence_check 算置信度 → A 路自动通过 / B 路低置信度送专家 / C 路触发硬规则必送专家；
   - 专家复评后，差异大的课例**脱敏回流入向量库**（`recycle.py`），下一次类似课例自动参考。
   - 这不是"AI 打分"，是"AI 当助教、专家当主编、知识库自我进化"——目前检索到的文献里没有同构方案。
2. **感知档案全链路可追溯**：每个 trial 的 ASR/OCR/pose/timeline 原始 JSON 落盘，答辩时可以点开一个 trial，看到"系统凭什么给这个分"——这是大多数 demo 做不到的。
3. **长期记忆 + 成长曲线**：跨次试讲追踪短板，你截图里的成长曲线就是这个功能的产品化。

### 8.3 实用性（25%）—— 现在最弱，要补

- **用户量为 0**：除了你自己和 sandbox，没有真实师范生用过。Week 3 至少找 3–5 个同学录 1 次试讲，收问卷。
- **没有"不替代导师"的产品化表达**：免责提示在报告开头，但登录后没有 onboarding 说明。加一个 30 秒动画讲清楚"这是练手工具，不是裁判"。
- **训练建议不可执行**：现在 training_plan 是 LLM 一段话，要改成"下周练 3 次导入、每次 1 分钟、参考 XX 课例"这种可勾选清单。

### 8.4 用户体验（15%）—— 视觉已经够，缺状态反馈

- 上传 20 分钟视频时**必须有进度条**（现在没有，会以为死机）。
- 报告页要把"机器分 vs 专家分"的偏差可视化（现在复评页有，但学生端看不到老师改了哪几项）。
- 空状态：新用户第一次登录不要看到一堆 mock 数据，要引导录第一段视频。

## 九、立即可以动手的 5 件事（按 ROI 排序）

1. **D1 修评分随机性**：temperature→0.05 + 同视频跑 5 次记录方差。这是你现在最焦虑的问题，也是评委最容易挑的点。
2. **F1–F4 清掉 mock**：上传历史列表、两个聊天面板、workbench 的 mock import。半天工作量，但"看起来像真系统"全靠这个。
3. **异步任务队列**：不做这个，20 分钟视频一上传就超时，后面所有测试都跑不了。
4. **OCR/pose 长视频采样修复**：现在的参数在 20 分钟视频上等于瞎子。
5. **拿 1 条青教赛视频跑通全流程**：不要等 10 条，先跑通 1 条，记录每步耗时和报告质量，再决定要不要调架构。
