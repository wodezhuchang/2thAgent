# 人机协同评价工作流改造计划书 v1.0

> 编写日期：2026-10-27
> 基于现有代码（backend/app/）与多轮架构讨论敲定
> 目标：从"端到端全自动评价"改造为"机器初评 + 智能分流 + 专家异步复评"的人机协同模式

---

## 一、背景与问题

### 1.1 现状
当前系统（v0.2.0）是一条线性工作流：
视频上传 → 多模态感知（ASR/OCR/timeline/pose）→ LangGraph 9节点串行 → 一次性返回完整评价报告。

### 1.2 问题
文献与实际测试表明：纯端到端全自动评价在真实教学场景下存在三个硬伤：
1. **LLM 自评不可靠**：现有 `reflect` 节点让 LLM 自己检查自己，缺乏量化置信度，无法区分"高把握"和"瞎猜"。
2. **无分流机制**：所有试讲都走同一条路，简单的和复杂的、证据充分的和证据缺失的，都给同一份报告，专家无法介入。
3. **无专家闭环**：教师的专业判断无法回流到系统，系统不会越用越准。

### 1.3 改造目标
- 引入**置信度**：每个维度的评价都附带客观可算的置信度。
- 引入**智能分流**：按证据链完整度自动分级，低风险自动过、中风险推专家、高风险强制告警。
- 引入**专家异步复评**：不阻塞学生主线，专家意见通过消息系统异步送达。
- 引入**数据回流**：专家标注的分歧样本进入知识库，系统持续校准。

---

## 二、核心设计决策（已敲定）

### 2.1 不拆多Agent并行打分
保留一个 Judge Agent（现有 `evaluator.py`）统一打分。课标RAG只提供证据不打分，虚拟学生Agent远期再做。
**理由**：多个Agent各自打分标准不一，算"分数方差"是假分歧，会导致专家工作台被正常的视角差异淹没。

### 2.2 分流依据：证据链完整度，不是分数方差
- **条件A（自动通过）**：所有维度证据齐全 + 置信度 > 0.7 → 机器报告直达学生，留10%抽查。
- **条件B（推专家复评）**：任一维度证据缺失或证据与分数矛盾 → 推送到专家复评工作台。
- **条件C（强制告警）**：硬规则触发（互动次数<2次、最长无互动独白>60s、时间轴缺环节、板书为空等）→ 推送教研室主任。全部基于已跑完的ASR/timeline/OCR结果事后统计，不增加工作流延迟。

### 2.3 置信度用客观信号算，不让LLM自评
```
某维度置信度 = 证据成功率 × RAG支持度 × 时间轴覆盖度
```
- 证据成功率：该维度对应的感知工具是否成功（ASR成功=1.0，失败=0.3）
- RAG支持度：是否召回了该维度相关的课标/量表依据
- 时间轴覆盖度：该维度评价是否有时间轴证据支撑

### 2.4 专家复评是旁路，不阻塞主图
- 主图 `graph.run_agent()` 跑完立即返回机器报告，状态标记为 `pending_expert`。
- 专家复评是独立 HTTP 接口，异步提交，不阻塞学生上传下一个视频。
- 学生先看到机器反馈，专家意见回来后通过消息系统通知。

### 2.5 成长曲线用机器分做趋势，专家分做校准锚点
- 成长曲线始终读机器分（`overall_percent`），保证趋势连续不断档。
- 专家分不回改历史点（学生当时看到的反馈是真实的）。
- 攒够样本后计算系统偏差（如"机器在D2语言维度平均偏高2分"），后续机器分自动校准。

### 2.6 专家意见走消息系统，不混进新报告
- 每次试讲的报告页面独立。专家意见回来后更新的是那个试讲自己的页面。
- 学生通过铃铛红点查看历史专家反馈，点消息跳转到对应试讲详情页。
- 上传新视频时不会冒出历史专家意见，保持当前报告干净。

### 2.7 专家意见回流知识库
- 机器分与专家分差异 > 10分的样本 → 入RAG案例库，标注"专家修正案例"。
- 差异 < 10分 → 不入库（一致，无学习价值）。
- 攒够50个分歧案例后，可用于Judge Agent的DPO微调。

## 三、分阶段实施计划

### 第一阶段：置信度 + 分流规则（不拆Agent，不动主图结构）

**目标**：在现有工作流上增加置信度计算和分流节点，专家复评先做简陋版（管理后台列表）。

**改动清单**：

| 文件 | 改动内容 |
|---|---|
| `app/evaluator/evaluator.py` | `eval_all_dimensions` 返回结果里增加每个维度的 `confidence` 字段 |
| `app/rag/retriever.py` | `retrieve()` 返回结果里增加每个召回片段与维度的相关性标记 |
| 新建 `app/evaluator/evidence_check.py` | 新增：检查每个维度的证据链完整度，输出置信度和缺口列表 |
| `app/graph/graph.py` | 在 `node_synthesize` 之后、`node_reflect` 之前插入 `node_triage` 分流节点；根据置信度走条件边 |
| `app/graph/state.py` | `AgentState` 增加 `confidence: dict`、`triage_result: dict` 字段 |
| `app/memory/memory_store.py` | `evaluation` 表加 `review_status` 字段（默认 `pending`） |
| `app/main.py` | 加 `GET /api/triage/pending` 接口：列出待专家复评的试讲列表 |

**分流节点逻辑（node_triage）**：
```python
def node_triage(state):
    confidence = state["confidence"]  # {D1: 0.8, D2: 0.4, D3: 0.9, D4: 0.7}
    min_conf = min(confidence.values())
    
    # 条件C：硬规则（全部基于已跑完的ASR/timeline/OCR结果做事后统计，零额外延迟）
    if detect_hard_risk(state["multimodal"]):
        state["triage_result"] = {"route": "C", "reason": "hard_risk",
                                   "risks": detect_hard_risk(state["multimodal"])}
    # 条件B：任一维度置信度 < 0.5
    elif min_conf < 0.5:
        state["triage_result"] = {"route": "B", "reason": "low_confidence",
                                   "weak_dims": [d for d, c in confidence.items() if c < 0.5]}
    # 条件A：全部 > 0.7
    else:
        state["triage_result"] = {"route": "A", "reason": "auto_pass"}
    
    return {"triage_result": state["triage_result"]}
```

**流程说明**：triage 节点不分叉主链，只把分流结果（route/reason/weak_dims）存入 state。
之后无论哪条路，都继续走 `reflect → memory_write → finalize`。
区别只在 `memory_write` 落库时：
- A路 → `review_status = 'auto_pass'`
- B/C路 → `review_status = 'pending_expert'`

这样主链仍然是线性的，不需要条件边，改动最小。

**条件C硬规则（detect_hard_risk）具体定义**：

全部基于已跑完的ASR/timeline/OCR结果做事后字符串匹配和计数，不增加工作流延迟：

| 规则 | 阈值 | 检测方式 |
|---|---|---|
| 互动次数过少 | 提问词出现 < 2次 | 在ASR文本里数"大家看/谁来说/请同学/想一想/谁来回答"等词 |
| 最长无互动独白 | 连续两个提问词之间 > 60s | 从ASR segments里算最长无提问间隔 |
| 时间轴环节缺失 | 缺"小结"或缺"练习"环节 | 直接看timeline_slice返回的phases列表 |
| 板书为空 | OCR板书字数 < 10 | 统计board_text的字符数 |

触发任一即返回风险列表。

**验收标准**：
- [ ] 每次评价返回的报告里包含每个维度的置信度
- [ ] 低置信度的试讲在管理后台能看到待复评列表
- [ ] 高置信度的试讲自动通过，不进待复评列表
- [ ] 条件C硬规则检测不增加工作流总耗时（全部基于已有结果事后统计）
- [ ] 主图仍然是同步跑完返回，不阻塞

### 第二阶段：专家复评闭环 + 消息系统

**目标**：专家能在工作台复评，学生能收到消息通知，人机差异能记录。

**改动清单**：

| 文件 | 改动内容 |

| `frontend/` | 学生端：报告页加"专家复核"区块（如果review_status=expert_reviewed则展示）；导航栏加消息铃铛 |
| `frontend_Admin/` | 新建专家复评工作台页面：待复评列表 → 机器初评摘要+时间轴证据 → 专家填复评意见 → 提交 |

**数据库Schema变更**：
```sql
-- 新增：专家复评表
CREATE TABLE expert_review (
    review_id      TEXT PRIMARY KEY,
    try_id         TEXT,
    expert_id      TEXT,
    reviewed_at    TEXT,
    final_scores   TEXT,        -- 专家权威分（JSON）
    comments       TEXT,        -- 专家原文意见（完整保留）
    disagree_dims  TEXT,        -- 分歧维度列表
    score_deltas   TEXT         -- 机器分 vs 专家分差异
);

-- 新增：消息表
CREATE TABLE message (
    message_id     TEXT PRIMARY KEY,
    user_id        TEXT,
    type           TEXT,        -- expert_review_ready
    related_try_id TEXT,
    title          TEXT,
    content        TEXT,
    is_read        INTEGER DEFAULT 0,
    created_at     TEXT
);

-- evaluation表加字段
ALTER TABLE evaluation ADD COLUMN review_status TEXT DEFAULT 'pending';
-- pending=待专家 / auto_pass=自动通过 / expert_reviewed=专家已复评
ALTER TABLE evaluation ADD COLUMN expert_score REAL;
ALTER TABLE evaluation ADD COLUMN calibration_note TEXT;
```

**专家提交复评后的后置逻辑**：
1. 写 `expert_review` 表
2. 更新 `evaluation.review_status = 'expert_reviewed'`
3. 计算机器分 vs 专家分差异，写 `score_deltas`
4. 如果差异 > 10分，写一条 `message` 给学生："你第N次试讲的专家复核已完成"
5. 如果差异 > 10分，把这个样本加入RAG案例库（标注"专家修正案例"）

**验收标准**：
- [ ] 专家能在工作台看到待复评列表，点开能看到机器初评摘要和时间轴证据
- [ ] 专家提交复评后，学生端消息铃铛出现红点
- [ ] 学生点消息能跳转到对应试讲详情页，看到机器+专家意见并列
- [ ] 上传新视频时不会冒出历史专家意见
- [ ] 分歧大的样本自动进入RAG案例库

### 第二阶段补充：chat 聊天助手后端（前端暂缓）

**定位**：一个"精通试讲的朋友"角色，不是通用聊天机器人。学生可以边看报告边问，也可以日常聊进步状态。

**原则**：后端接口和数据库表在本阶段建好并用 Postman 测试，但前端聊天面板不做，等后续前端大改造时再嵌页面。

**能力清单**：

| 类别 | 功能 | 举例 | 数据来源 |
|---|---|---|---|
| 查自己 | 历史试讲回顾 | "我上次试讲多少分""D3板书还有什么问题" | memory_store |
| 查自己 | 成长趋势解读 | "我这几次进步了吗""哪个维度进步最大" | memory_store 成长曲线 |
| 查自己 | 训练计划追踪 | "我这周该练什么""上次计划完成了吗" | memory_store.training_plan |
| 怎么练 | 针对性练习建议 | "口头禅太多怎么改""板书布局怎么练" | RAG 教学方法库 + 用户短板 |
| 怎么练 | 教案讨论 | 贴一段教案 → 导入设计合理吗 | RAG 评课标准 |
| 怎么练 | 临场问题应对 | "上台紧张怎么办""学生问我答不上来" | RAG 教学策略库 |
| 陪练 | 模拟评委提问 | "你是评委，问我一个问题" → 学生答 → 给反馈 | LLM 生成 |
| 陪练 | 时间规划 | "下周比赛，帮我排个练习计划" | 用户短板 + 剩余时间 |
| 状态 | 情绪支持 | "我觉得练不好了" → 朋友式鼓励 + 实际建议 | 用户画像 |

**风格要求**：
- 不说"作为一个AI助手"，不说"建议你可以考虑"
- 说人话，有具体动作："你上次导入讲了3分钟还没进正题，下次试试抛一个问题，1分钟引出课题"
- 先共情再给建议，不空洞鼓励

**技术实现**：

```
POST /api/chat
  ├─ 1. 读用户画像：最近3次试讲分数、当前短板、训练计划
  ├─ 2. 意图识别（轻量规则）
  │     ├─ 含"我上次/最近/进步/分数" → 查 memory_store
  │     ├─ 含"怎么练/怎么办/教案" → 查 RAG
  │     ├─ 含"模拟/陪练/排计划" → 直接生成
  │     └─ 其他 → 直接聊
  ├─ 3. 根据意图决定要不要查库
  ├─ 4. 组装 prompt：角色设定 + 用户画像 + 对话历史 + 检索结果 + 当前消息
  ├─ 5. 调 llm_client.chat() 生成回复
  └─ 6. 存 chat_message 表
```

**复用现有模块**：不新建 LLM 客户端、不新建 RAG，直接调 `llm_client.py` 和 `retriever.py`。

**数据库表**：
```sql
CREATE TABLE chat_message (
    message_id   TEXT PRIMARY KEY,
    user_id      TEXT,
    role         TEXT,        -- user / assistant
    content      TEXT,
    intent       TEXT,        -- self_progress / how_to_practice / state_check / casual
    session_id   TEXT,        -- 同一次对话的session，跨天自动开新session
    created_at   TEXT
);
```

**对话规则**：
- 同一次登录内延续对话（同一个 session_id）
- 跨天自动开新 session，但历史记录可查
- 第一版不支持发图片（长期备选功能）

> **落地状态（2026-10-30）**：后端 `/api/chat` 已改为 **POST** 非流式（原误用 GET 不支持请求体）；新增 `/api/chat/sessions`（会话列表聚合：标题/首条 intent/起止时间/消息数）与 `/api/chat/sessions/{session_id}`（完整对话回看）。前端已建独立**学生端 chat 页 `/student/chat`**：左列会话列表按**主题分类**（查成绩/怎么练/模拟陪练/状态调整/随便聊聊，取自首条消息 intent）+ **时间筛选**（全部/今天/近7天/更早），右侧对话窗口支持新建/延续，点开会话可回看完整历史（每条消息带时间戳）。验收清单新增：前端会话列表分类正确、点开会话可回看完整对话。

**验收标准**：
- [ ] Postman 调 `/api/chat` 能拿到回复
- [ ] 问"我上次试讲多少分"能正确从 memory_store 取数据
- [ ] 问"板书怎么练"能正确从 RAG 检索教学方法
- [ ] 对话记录写入 chat_message 表
- [ ] 回复风格像朋友，不像AI客服

### 第二阶段补充：专家端 chat 教研助手（2026-10-28 新增）

**定位**：专家工作台的内置教研助手，不是陪聊。角色是"严谨的教研员"，给数据、给依据、给参考，不陪聊。

**和学生端 chat 的区别**：

| 维度 | 学生端 chat | 专家端 chat |
|---|---|---|
| 角色 | 陪练朋友，说人话 | 教研助手，严谨专业 |
| 数据权限 | 只能看自己的历史 | 能看指定学生的历史、全班统计、课标库 |
| 核心场景 | 怎么练、情绪支持、查自己 | 查学生历史、课标参考、评语辅助 |
| 风格 | 朋友式，先共情再建议 | 直接给数据和依据，不寒暄 |

**功能清单**：

| 类别 | 功能 | 举例 | 数据来源 |
|---|---|---|---|
| 查学生 | 学生历史表现 | "这个学生之前试讲过几次？进步趋势怎么样？" | memory_store |
| 查学生 | 对比同班学生 | "这个学生的D2语言维度在班里什么水平？" | memory_store 全班统计 |
| 查课标 | 评课标准查询 | "初中数学一次函数的课标要求是什么？" | RAG 课标库 |
| 查课标 | 指标解读 | "D3板书这个指标，优秀标准是什么？" | RAG 评课量表 |
| 辅助 | 评语草稿 | "根据这些观察帮我写一段评语" | 专家输入观察点 + LLM生成 |
| 辅助 | 分歧分析 | "机器分41，我打了48，差7分，哪里可能有问题？" | 机器分证据链 + LLM分析 |

**技术实现**：
```
POST /api/expert-chat
  ├─ 1. 读专家身份（expert_id）
  ├─ 2. 读指定学生的画像（可选 student_id）
  ├─ 3. 意图识别：
  │     ├─ 含"这个学生/他之前/进步/历史" → 查 memory_store
  │     ├─ 含"课标/标准/要求/优秀" → 查 RAG
  │     ├─ 含"评语/写一段/帮我写" → LLM 生成
  │     └─ 含"分歧/差异/为什么差" → 证据链分析
  ├─ 4. 组装 prompt：教研员角色 + 学生数据 + 课标依据
  └─ 5. 调 LLM 生成回复
```

**数据库表**：复用 chat_message 表，加 `chat_type` 字段区分 student / expert。

**验收标准（2026-10-28 已完成）**：
- [x] 问"这个学生之前试讲过几次"能正确返回学生历史（student_history 意图）
- [x] 问"课标要求是什么"能正确从 RAG 检索（curriculum_ref 意图）

### 第三阶段：系统校准 + 知识库回流（远期）

**目标**：攒够数据后自动校准机器分，DPO微调Judge Agent。

**改动清单**：

| 模块 | 内容 |
|---|---|
| 偏差计算 | 每攒10个专家复评，计算每个维度的系统偏差（机器分均值 - 专家分均值） |
| 自动校准 | 后续机器分展示时自动减去系统偏差，标注"已校准" |
| DPO微调 | 攒够50个分歧案例后，用专家意见做偏好数据，微调Judge Agent |
| 虚拟学生Agent | 远期新增：模拟学生视角输出定性反馈，不打分 |
| 表情情感识别 | 远期新增：MediaPipe Face Landmarker，补充D4教态评价 |

**验收标准**：
- [ ] 成长曲线能展示"原始机器分"和"校准后估计分"两条线
- [ ] 专家复评数量在管理后台可见，系统偏差自动更新
- [ ] RAG案例库里能看到"专家修正案例"分类

## 四、前端交互设计

### 4.1 学生端
- **上传视频后**：立即看到机器初评报告（顶部标注"AI初评·待专家复核"或"AI初评·已自动通过"）
- **消息铃铛**：右上角，有未读消息时红点。点开看到消息列表，每条关联一个试讲。
- **试讲详情页**：如果 `review_status=expert_reviewed`，页面分两块：
  - 上半部分：机器初评（分数+评语）
  - 下半部分：专家复核意见（原文保留，标注专家姓名和时间）
- **成长曲线页**：始终用机器分画趋势线，专家复评过的点加个小标记。

### 4.2 专家工作台（管理后台）
- **待复评列表**：按时间排序，显示试讲标题、学科、机器总分、最低置信度维度
- **复评页面**：
  - 左侧：机器初评摘要（各维度分数+置信度+评语）
  - 中间：视频证据时间轴（可点击跳转到对应时间点）
  - 右侧：专家复评表单（调整分数、填写意见、标注分歧维度）
- **提交后**：自动计算人机差异，触发消息通知和知识库回流。

## 五、风险与回退

| 风险 | 应对 |
|---|---|
| 置信度公式不准，导致该推专家的没推 | 第一阶段先跑2周，人工核对分流结果，调整阈值 |
| 条件C硬规则误报（把正常试讲判为高风险） | 阈值先保守（60s/2次），跑2周后根据实际试讲数据调整 |
| 专家复评太慢，积压太多 | 工作台显示积压数量，超阈值时自动降级（超过48小时未复评的，自动按机器分给学生） |
| 消息通知打扰学生 | 纯靠铃铛红点，不弹窗不推送，学生主动看 |
| 专家意见和机器意见差异太大，学生困惑 | 报告页明确标注"机器初评"和"专家复核"是两个独立判断，不混为一谈 |

## 六、不做的事（明确边界）

- **不拆多Agent并行打分**：第一、二阶段都不拆，保留单Judge Agent。
- **不做实时WebSocket推送**：消息用轮询，学生打开前端时拉未读数。
- **不做虚拟学生Agent**：远期第三阶段再考虑。
- **不做表情情感识别**：远期第三阶段再考虑。
- **不回改历史成长曲线**：专家分不覆盖历史机器分，只做校准标注。
- **不阻塞主图**：专家复评永远是旁路，主图跑完就返回。
- **不做chat前端页面**：本阶段只建chat后端接口和数据库表，前端聊天面板等后续大改造时再嵌。
- **不做chat发图片**：第一版只支持文字对话，图片识别作为长期备选功能。
