# 多角色前端改造计划书 v1.0

> 项目：师范生试讲智能评价 Agent
> 日期：2026-10-29
> 状态：待评审 / 定稿后执行
> 范围：多用户逻辑加入后的**后端 + 前端**整体改造，按顺序**先后端后前端**
> 审计方式：本计划书为唯一事实来源，实施过程以「决策记录（R）」逐条核销

---

## 1. 背景与现状

### 1.1 现状
- **单租户硬编码**：前端多处写死 `user_id = 'demo_user'`（home / evaluate / growth / workbench / report）。
- **无账号体系**：没有 user 表、没有真实登录鉴权，任何访问均以 demo_user 视角运行。
- **全局 pending**：`/api/triage/pending` 返回全机构待复评，不区分专家归属。
- **Home 无角色区分**：所有角色看到同一张总览卡（4 个统计 + 3 个入口），信息不对口。
- **评价无归属**：evaluation 表没有 student_id / expert_id，无法定位"谁试讲、推给谁"。

### 1.2 目标
引入三档角色体系，建立账号 / 师生关系 / 评价归属 / 专家分发，并实现角色感知的 Home 与登录鉴权，使系统从"单用户演示"演进为"单机构内多人真实使用"。

## 2. 决策记录（R · 可审计）

| 编号 | 决策 | 理由 |
|---|---|---|
| R1 | 单机构内多人使用，**不做 org 多租户** | 用户拍板；避免过度设计 |
| R2 | 存储用 **SQLite**（沿用现有 memory_store），结构化关系型 | 单机构规模、低并发、零新增依赖、部署最简 |
| R3 | 角色三档：**全知全能(admin) / 师范生(student) / 教师(teacher)**，开发者并入全知全能 | 用户拍板 |
| R4 | 数据改造与登录鉴权**一块做**，但按顺序**先后端后前端**，单一文档承载 | 用户拍板；避免文档碎片化 |
| R5 | 虚拟测试账号与真实账号**同库**，用 `account_type`(real/sandbox) 区分 | 单机构内需开发者造虚拟师生测试，但不混入真实视图 |
| R6 | 师生关系用 **teacher_student 指导关系表** | 师范场景"一位师范生对应一位指导专家"最贴合，且是分发依据 |
| R7 | 评价分发闭环：**落库解析 expert_id → pending 按专家过滤 → 消息定向推送** | 确保"学生试讲推给对应专家" |
| R8 | 登录默认进**全知全能 Home（全景首屏）** | 演示与真实使用均自然，评委首屏看全貌 |
| R9 | 登录鉴权复用 **Soybean 现成能力**（登录页 / pinia auth store / 路由守卫），后端补真实登录接口 | 前端零成本复用框架，后端负责校验与签发 token |
| R10 | 师生关系由「**线下协商 → 线上凭教师邀请口令申请 → 教师确认**」建立（方案 B）；发送试讲时**显式指定老师**并做绑定校验；教师可**退回**误发/超范围试讲 | 用户拍板：未绑定不应发给无关专家；**学生端不暴露老师池，凭口令申请防恶意骚扰**；显式指定+确认弹窗降低错发概率；退回降低错发影响 |

## 3. 角色体系设计

### 3.1 三档角色定义
| 角色 | role | 定位 | 数据范围 |

## 4. 后端改造计划（先做）

### 4.1 表结构（SQLite，在现有库上新增/加列）

**新增 `user` 表**
```sql
CREATE TABLE user (
  user_id      TEXT PRIMARY KEY,
  username     TEXT UNIQUE NOT NULL,      -- 登录名
  password_hash TEXT NOT NULL,            -- bcrypt/pbkdf2 哈希
  name         TEXT NOT NULL,             -- 显示名
  role         TEXT NOT NULL,             -- admin / student / teacher
  account_type TEXT NOT NULL DEFAULT 'real',  -- real / sandbox
  org          TEXT DEFAULT '',           -- 机构名
  invite_code  TEXT,                      -- 教师邀请口令（学生凭它申请绑定）
  created_at   TEXT NOT NULL
);
```
> 说明：`user` 表在现有库上经迁移补列（username / password_hash / role / account_type / org / invite_code）。`invite_code` 为教师邀请口令，`create_user(role='teacher')` 时自动生成（8 位去易混淆字符），旧教师账号由 `ensure_invite_code` 兜底补发；学生账号无口令。

**新增 `teacher_student` 表（指导关系，分发依据；确认后写入）**
```sql
CREATE TABLE teacher_student (
  teacher_id TEXT NOT NULL,
  student_id TEXT NOT NULL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (teacher_id, student_id)
);
```

**新增 `binding_request` 表（方案 B：申请 → 确认 → 生效）**
```sql
CREATE TABLE binding_request (
  student_id  TEXT NOT NULL,
  teacher_id  TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending',  -- pending / accepted / rejected
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  PRIMARY KEY (student_id, teacher_id)
);
CREATE INDEX idx_binding_req_teacher ON binding_request (teacher_id, status);
```
> 说明：`binding_request` 为幂等申请记录（同一对学生-老师重复申请不报错）；教师 `confirm` 时写 `teacher_student` 并置 `accepted`，`reject` 置 `rejected`。

**业务表加列（ALTER TABLE）**
- `evaluation`：加 `student_id`、`expert_id`（谁试讲、推给哪位专家）
- `message`：加 `recipient_id`（定向推送对象）

### 4.2 接口改造 / 新增（与后端实际实现一致）
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | 校验账号 → 签发 token（JWT），返回 user 信息+角色 |
| GET | `/api/auth/me` | 按 token 返回当前用户（登录态恢复） |
| POST | `/api/evaluate` `/api/evaluate_video` | 入参含 `expert_id`（显式指定发送老师）；未指定 → 400「请先指定发送给哪位老师」；未与发送对象绑定 → 400「该老师与你尚未建立绑定关系」 |
| GET | `/api/triage/pending?expert_id=X` | 按专家过滤（教师只看推给自己的；admin 可全量） |
| GET | `/api/users?role=teacher` | 老师池（admin/内部使用；**学生端不展示**，防恶意申请） |
| POST | `/api/bindings/request` | 发起绑定申请（内部/保留；学生端主入口改凭口令申请） |
| POST | `/api/bindings/apply-by-code` | 学生凭教师线下提供的**邀请口令**申请绑定（解析口令→该校→发起申请；无效口令拒绝） |
| GET | `/api/users/{user_id}/invite-code` | 查询/生成教师邀请口令（教师端展示并线下告知指定学生） |
| GET | `/api/bindings/requests?student_id=&teacher_id=&status=` | 查询绑定申请（学生/教师双视角，含姓名） |
| POST | `/api/bindings/confirm` | 教师确认绑定（写 `teacher_student` + 申请置 `accepted`） |
| POST | `/api/bindings/reject` | 教师拒绝绑定（申请置 `rejected`） |
| GET | `/api/users/{user_id}/teachers` | 查询某学生已绑定老师（发送下拉数据源） |
| POST | `/api/expert-review/return` | 教师退回试讲（`review_status=returned`，向学生发「试讲被退回，请重新上传给正确的老师」消息，不指明具体老师） |
| GET | `/api/messages?user_id=` | 按 recipient_id 定向返回 |

### 4.3 分发逻辑（R7 闭环 · 方案 B：显式指定 + 绑定校验 + 退回）
1. 师生关系建立走「口令申请-确认」：教师端展示**邀请口令**（`invite_code`）并线下告知指定学生；学生凭口令 `POST /api/bindings/apply-by-code` 申请到该老师（**学生端不显示老师池**，无口令无法申请，防恶意骚扰），教师确认后写入 `teacher_student`（`is_bound=True`）；确认前不产生任何发送关系。
2. 发送试讲时**学生显式指定 `expert_id`**（对应已绑定老师），后端校验 `is_bound`：未指定 → 400「请先指定发送给哪位老师」；未绑定 → 400「该老师与你尚未建立绑定关系」。不再自动解析。
3. `/api/triage/pending?expert_id=`：教师 → 仅返回 `expert_id=自己` 的记录；admin（不传 expert_id）→ 全量 / 公共池复核。
4. 教师端可 `POST /api/expert-review/return` 退回误发/超范围的试讲：`review_status='returned'`，按 student 定向推送「试讲被退回，请重新上传给正确的老师」（不指明具体老师）；校验非本人试讲不可退回。
5. 消息：评价完成 / 复评完成 / 退回按 `recipient_id` 定向推送给对应学生或教师。

### 4.4 认证与安全
- token：JWT（含 user_id / role / 过期时间），密钥存后端配置。
- 密码：bcrypt/pbkdf2 哈希，不落明文。
- 登录接口校验失败统一返回 401。

- 复用 Soybean 登录页与 `useAuthStore`（现有 mock 登录 → 改为真实 `POST /api/auth/login`）。

## 8. 待决项 / 风险

| 项 | 说明 | 建议 |
|---|---|---|
| 密码加密库 | passlib 依赖 | 若未装，用 hashlib.pbkdf2_hmac 内建实现，零依赖 |
| token 有效期 | 演示期 | 设较长（如 7 天），上线前收紧 |
| 已有存量评价的归属 | 历史 evaluation 无 student/expert_id | 新评价走新逻辑；存量标记为 admin 公共池，不回填 |
| sandbox 虚拟账号来源 | 由 admin 手动创建 | 提供 admin 建号入口，或 seed 脚本预置 |
